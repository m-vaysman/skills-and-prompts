The Model Will Open the Class

A real EF Core example of why “extend, don’t edit” has to be made operational for coding agents.

Michael Vaysman · September 2026 · the pull request on GitHub

I did not invent this.

Open/Closed is the O in SOLID: a type should be open for extension and closed for modification. You add behavior beside what already shipped. You do not open the shipped class and type inside it. I learned that years ago, the same way every other .NET developer did. I am not here to teach it.

What interests me is something more practical: an AI coding agent will often violate this rule unless you make the rule concrete.

Not because it does not know SOLID. Ask it about Open/Closed and it will explain it perfectly. The problem appears when there is a ticket to finish.

The shortest path is modification.

Find the class that already does almost what you need. Open it. Add an if. Add a constructor parameter. Add another dependency. Put a provider check into an existing configuration. Make the tests green.

Locally, this often looks reasonable.

Architecturally, it slowly turns stable code into the place where every future requirement goes to live.

A real ticket

I recently gave an agent a straightforward change to an existing .NET application: add PostgreSQL as an optional database provider while leaving SQL Server as the default.

The application already had an EF Core DbContext, entity configuration, SQL Server registration, migrations, tests, an API host, and a worker.

This is exactly the sort of request where modification is tempting.

PostgreSQL disagreed with several SQL Server-specific mappings:

  • varbinary(max) needed to become PostgreSQL bytea.
  • nvarchar(max) needed to become text.
  • An index filter used SQL Server identifier quoting.
  • A calendar value needed PostgreSQL's date mapping.
  • PostgreSQL's provider imposed stricter UTC handling for timestamps.

There is an obvious implementation.

The obvious implementation

Open the existing EF configuration and teach it about both databases.

// Existing configuration

if (provider == DatabaseProvider.Postgres)
{
    property.HasColumnType("bytea");
}
else
{
    property.HasColumnType("varbinary(max)");
}

Repeat that wherever the providers disagree.

if (postgres)
{
    index.HasFilter("\"EmailMessageId\" IS NOT NULL");
}
else
{
    index.HasFilter("[EmailMessageId] IS NOT NULL");
}

Perhaps add the provider to the DbContext. Perhaps pass configuration farther down. Perhaps make the old registration method smart enough to understand another database.

None of these changes is insane.

That is why this problem matters.

Bad architectural drift rarely arrives as obviously bad code. It arrives as a sequence of reasonable edits to code that already worked.

The constraint

For this work, the existing OmsLoanDbContext, entity configurations, and SQL Server registration were treated as closed.

The instruction was effectively:

EXTEND

The old implementation is read-only.

You may add new files.
You may add tests.
You may change composition where the application is already wired.

If the requested behavior requires changing the locked implementation,
stop and report that the seam is missing.

This changes the agent's problem.

The question is no longer:

Where can I put the PostgreSQL behavior?

It becomes:

What extension seam already exists?

That is a much better question.

EF Core already had the seam

The agent found IModelCustomizer.

EF Core builds its model and exposes a framework-level customization point. The PostgreSQL path could therefore allow the existing model to be built normally, then apply only the PostgreSQL-specific differences afterward.

A new type was added:

public sealed class PostgresModelCustomizer
    : ModelCustomizer
{
    public override void Customize(
        ModelBuilder modelBuilder,
        DbContext context)
    {
        base.Customize(modelBuilder, context);

        // PostgreSQL-specific overrides live here.
    }
}

That call to base.Customize is the important part.

The existing model still builds itself. The existing SQL Server configuration does not need to know PostgreSQL exists.

The new provider adds its differences afterward.

For example:

modelBuilder.Entity<Notice>()
    .Property(n => n.Content)
    .HasColumnType("bytea");

modelBuilder.Entity<Extraction>()
    .Property(e => e.RawJson)
    .HasColumnType("text");

The old configuration did not become:

SQL Server + PostgreSQL + every provider we may support someday

It remained the thing it already was.

The provider installs the extension

The PostgreSQL registration then tells EF Core to replace the normal model customizer only when the PostgreSQL path is selected.

return options
    .UseNpgsql(connectionString, npgsql =>
        npgsql.MigrationsAssembly(postgresAssembly))
    .ReplaceService<IModelCustomizer, PostgresModelCustomizer>();

This is what extension looks like in a framework-heavy application.

No inheritance hierarchy had to be invented. No artificial interface had to be placed around the application's own classes. No textbook pattern had to be forced into the design.

The framework already provided a seam.

The job was to find it.

The old path remained the old path

Provider selection was added outside the existing SQL Server implementation.

Conceptually:

if (provider is missing or SqlServer)
    use existing SQL Server registration;

if (provider is Postgres)
    use new PostgreSQL registration;

Notice what did not happen.

The old SQL Server registration was not rewritten to become a universal database factory. The new layer delegates to it unchanged when SQL Server is selected.

That distinction looks small in a diff. It is large in a codebase.

The composition root is allowed to know

Something eventually has to choose the implementation.

Before the change, the hosts contained essentially:

builder.Services.AddOmsLoanDbContext(connectionString);

Afterward:

builder.Services.AddOmsLoanDatabase(
    builder.Configuration,
    connectionString);

That is a modification, but it is not a violation of Open/Closed.

Composition is where choices belong.

If adding a new implementation were forbidden from changing the place where implementations are selected, almost no real system could ever be extended.

The useful rule is not “never modify any existing file.”

It is:

Do not put the new behavior inside the old implementation. Change only the place where the application chooses which implementation to use.

The diff tells the story

The resulting pull request added a separate OmsLoan.Data.Postgres project, PostgreSQL migrations, provider-selection code, Docker Compose configuration, documentation, and a dedicated test project.

The existing OmsLoanDbContext, existing entity configurations, and existing SQL Server registration were absent from the diff.

That is a useful review heuristic.

Expected EXTEND diff:

+ new implementation
+ new tests
+ provider-specific infrastructure
~ minimal composition wiring

  old implementation: untouched

You can almost evaluate the architecture before reading the code.

If the supposedly closed class appears in an EXTEND diff, there had better be an explanation.

The tests matter for a different reason

The new tests did not merely demonstrate that PostgreSQL worked.

They also demonstrated that the old path remained the old path.

[Theory]
[InlineData(null)]
[InlineData("")]
[InlineData("SqlServer")]
public void SqlServerIsUsedUnlessPostgresIsConfigured(...)
{
    // Resolve the context.

    Assert.Equal(
        "Microsoft.EntityFrameworkCore.SqlServer",
        context.Database.ProviderName);
}

Separate tests verified that selecting PostgreSQL resolved Npgsql.

That distinction is important.

An extension test should answer two questions:

  1. Does the new behavior work?
  2. Did we accidentally change the old behavior while adding it?

The pull request reported 395 passing tests, including 22 new tests covering provider selection, PostgreSQL mappings, UTC handling, preservation of the SQL Server model, and migration/model agreement.

A useful failure also appeared

One known limitation was left unresolved.

An invalid provider name causes a startup exception. Making that failure integrate cleanly with the application's existing startup validation would require changing an existing type on the established code path.

The agent did not quietly make that edit.

It identified it as separate CHANGE work.

This may be the most important behavior in the entire exercise.

Open/Closed does not mean every ticket can be completed by extension.

Sometimes the seam is missing.

The discipline is being able to say so.

Why agents need the rule stated this way

“Follow SOLID” is too abstract.

“Prefer Open/Closed” is too negotiable.

Under pressure to complete a task, a coding model can always explain why editing the existing class is simpler, smaller, safer, or more idiomatic.

Often it is simpler.

That is the problem.

The instruction that changed the outcome was mechanical:

The old type is locked.

If an extension seam exists, use it.

If no seam exists, stop.

Do not create the seam by editing the locked type.

Once modification was removed as the default escape hatch, the model had to inspect the architecture around the class.

And there was the seam: not hidden, not exotic, not invented for the exercise. EF Core had already provided it.

This changes what code review looks like

I increasingly think this is useful beyond AI.

Instead of beginning a review with:

Is this code good?

begin with:

Why did this existing file have to change?

Sometimes there is a good answer.

A bug is inside that type. Its contract is wrong. The architecture genuinely lacks the seam required for the new behavior.

Fine. Call that CHANGE.

But a new feature should not automatically inherit permission to rewrite the thing beside it.

Make the distinction explicit.

EXTEND and CHANGE

I now prefer tickets to have one of two meanings.

EXTEND

Existing production behavior is locked. Add new types beside it. Use existing interfaces, decorators, factories, framework hooks, middleware, strategies, providers, callbacks, or composition seams.

If the seam does not exist, stop.

CHANGE

A named existing type may be edited because the required seam does not exist or because that type itself is what the ticket intends to change.

CHANGE is explicit. It is scoped. It is not permission to clean up the neighborhood.

The lesson from the PostgreSQL change

The PostgreSQL pull request is not interesting because it contains an ingenious pattern.

It is interesting because it does not.

EF Core already knew how to be extended. The original application's classes did not need to be redesigned.

The agent simply had to be prevented from taking the easiest route long enough to discover the route the framework had already provided.

That is the practical version of Open/Closed I care about.

Not:

Can you explain the O in SOLID?

But:

There is a working class in front of you. The ticket asks for new behavior. Are you going to open it?

Left alone, the model often will.

Lock the class.
